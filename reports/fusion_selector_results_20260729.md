# 路线1 融合选择器实验报告（含流程图与细节图）

**日期**：2026-07-29 · **分支**：dev · **全盘验证，官方评测**

## 一、实验目标

融合两个独立系统的预测（merged4-agent 1073 + GLM-agent 967），利用它们失败集的不完全重叠（融合 oracle = 1146）提升 EX。核心挑战：**无 gold 信号下如何可靠选择**。

## 三、融合选择器细节图（GLM-judge 内部逻辑）

```
对每道两系统 SQL 不同的题 (1088题):
    ┌─────────────────────────────────────────┐
    │ 1. 分别执行 merged4-SQL 和 GLM-SQL      │
    │    → 得到两个执行结果 (rows/error)       │
    │                                         │
    │ 2. 随机 A/B 顺序排列两个 SQL+结果       │
    │                                         │
    │ 3. 构造 judge prompt:                   │
    │    Question + Evidence                  │
    │    + Candidate A SQL + Result A         │
    │    + Candidate B SQL + Result B         │
    │    → GLM-5.2 (thinking disabled)        │
    │    → 输出 {"winner": "A"/"B"/"tie"}     │
    │                                         │
    │ 4. 映射回 merged4/glm; tie→merged4      │
    └─────────────────────────────────────────┘
         结果: glm 赢 245, m4 赢 843
         但: rescue=61, damage=105, net=-44 ❌
```

## 四、三种融合策略结果对比

| 策略 | EX | rescue | damage | net | 结论 |
|---|---:|---:|---:|---:|:--:|
| merged4 单独（基线） | 1073 | — | — | — | — |
| A: merged4优先,空/err换GLM | 1074 | 1 | 0 | +1 | 几乎无效 |
| D: 信任GLM修正(分歧全换) | 967 | — | — | -106 | 灾难 |
| **GLM-judge (A/B盲选)** | **1029** | **61** | **105** | **-44** | **净损坏** |
| 融合 oracle (上限,需gold) | 1146 | 252 | 0 | +73 | 不可部署 |

## 五、结论

1. **GLM-5.2 作为自身 SQL 的 pairwise judge 不可靠**：它在 245 题上选了 GLM-SQL，但其中 105 题原本 merged4 是对的（被改坏），只有 61 题 GLM 确实更好（rescue）。净损坏 -44。
2. **根本原因**：两个系统的 SQL 通常都能执行成功（非空），执行结果不同但都"看起来合理"。GLM-5.2 无法判断哪个结果集才是问题真正想要的——这需要 gold 或更强的语义判别器。
3. **融合 oracle（1146）需要可靠选择器才能实现**，但当前所有无 gold 选择信号（执行有效性、行数、JOIN 数、GLM-judge）都无法可靠区分。
4. **唯一可能奏效的融合方式**：ORM-v2 重打分（把两个 SQL 都喂给 ORM 模型打分选高），但需要 GPU/vLLM（当前被 GRPO 占用）。

## 六、当前最佳合规分数不变

**merged4 + E3v + E4 = 1073/1534 = 69.95%** 仍是最佳合规结果。融合路线在无 GPU 重打分条件下不可行。
