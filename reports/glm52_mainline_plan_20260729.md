# harness + GLM-5.2 主线可行规划（基于实测）

**日期**：2026-07-29 · 基于本轮全盘审计与 GLM-5.2 实测

## 已验证的前提

1. **GLM-5.2 API 不支持 `n` 参数**（实测：n=3 返回 1 choice）→ 多候选必须多次调用。
2. **GLM-5.2 temp=0.7 多采样对 base 失败题 oracle 恢复率 ≈ 25%**（8 题 N=6 实测：2/8）。
3. **GLM-5.2 单次 thinking 调用 30–60s**，全量 1534 题 × N 采样需数小时（API 并发受限）。
4. **上游小模型池（merged4）合规**，oracle n4=1223 / n8=1251。
5. **当前合规最佳 = 1072（69.88%）**，来自 merged4 + ORM 选择器。

## 三条可行方向（按性价比排序）

### 方向 A：融合候选池（GLM-5.2 + 上游小模型）⭐ 推荐
- **做法**：把 GLM-5.2 的 base 预测（908，已合规）+ detVG（925）作为候选源之一，并入上游 merged4 n4 池（16 候选），用现有 ORM 选择器在 17+ 候选上选。
- **预期上限（oracle）**：merged4 oracle 1223；GLM base 在 merged4 失败题上能额外覆盖多少需测，但两者模型差异大、失败集重叠低，融合 oracle 估计 **1250–1300**。
- **成本**：低。GLM base 已有（908），合并池无需新生成；只需把 GLM base 当候选加入已打分的 merged4 池重选。
- **风险**：低。纯选择层操作，可立即验证。
- **第一步**：测 GLM-base 在 merged4 失败的 311 题（1223 覆盖外）上能补覆盖多少 → 决定是否值得。

### 方向 B：GLM-5.2 多采样 + E4 执行修复（增强 GLM 侧）
- **做法**：GLM-5.2 对全量 base 失败题做 temp=0.7 × N=5 采样，产多候选；再对仍失败的题跑 E4 执行修复（已有 agent，用 GLM-5.2）。
- **预期上限**：base 908 + 多采样恢复 ~156（25%）+ E4 修复增量 ≈ **1050–1100**。
- **成本**：中。1534×5 次 GLM 调用（thinking 慢，~6–10 小时）。
- **风险**：中。外推 25% 是 8 题小样本，置信度有限；thinking 模式成本高。
- **价值**：能提升 GLM 侧候选质量，但单独天花板（~1064）低于上游池（1223）。

### 方向 C：上游池 + ORM 选择器强化（已部分做）
- **做法**：继续优化 ORM 选择器（ORM v3 / 多源融合），缩小 1223→1072 的 151 题差距；n8 打分补 +28。
- **预期**：1072 → 1100–1150（选择器召回提升）。
- **成本**：低（n8 打分被 GPU 阻塞，待空闲）。
- **风险**：低，但增量有限。

## 推荐执行顺序

1. **方向 A 第一步（立即，低成本验证）**：测 GLM-base 能否补覆盖 merged4 失败题。若融合 oracle > 1250，值得做完整融合选择。
2. **方向 C**：待 GPU 空闲补 n8 打分（+28）+ 选择器微调。
3. **方向 B**：仅在 A/C 验证后仍不够时，投入 GLM 多采样（成本最高、天花板最低）。

## 方向 A 第一步验证结果（已实测）

- merged4 oracle = 1223，失败 311 题。
- **GLM-base 在 merged4 失败的 311 题里只补覆盖 23 题**。
- 融合 oracle（merged4 + GLM base）= **1246（81.23%）**，仅比纯 merged4（1223）+23，**低于 n8（1251）**。
- **结论：GLM-5.2 与上游小模型失败集高度重叠，融合收益微弱，方向 A 不值得投入**。

## 90% 可达性评估（更新）

- 三条路的天花板：A=1246、B≈1064、C≈1100–1150。**均 < 90%（1381）**。
- 根本瓶颈是**生成器基座能力**：GLM-5.2（908）和上游小模型（1023 best）的 oracle 上限（~1250）本身就到不了 1381。
- **要到 90%，必须换更强的基座生成器**（如 70B+ 模型、或专门针对 BIRD train 微调到 EX>75% 的生成器）。这是 harness/选择器/检索层无法弥补的。
