## 本周完成

### 1. 错题打标与高频错误族发现

对全部 321 道错题逐题自动打标，聚类出四大错误族：

- **列选错**（143 题，45%）：模型选错了要返回的列，比如题问"学校名"但模型返回了"学校全称"列（两个列名很像但数据不同），这是最大的错因；
- **JOIN 路径错**（81 题，25%）：多连了一张不必要的表（39 题）或漏连了需要的表（42 题），导致结果行数错或列数据错；
- **过滤值错**（51 题，16%）：WHERE 条件里用错了值，比如题说"Riverside 开头"但模型写了精确等于"Riverside"，或日期格式写错；
- **空结果**（30 题，9%）：正确答案有数据，但模型集体用错枚举值或错 JOIN 导致返回空，空结果在候选投票中成了多数派。

### 2. 选择器空结果降权处理

发现 27 道题的候选池里超过一半候选返回空结果，但正确答案非空——空结果投票压制了正确候选。对选择器做空结果降权（空候选分数打折），单独测试修对 1 题。修复率有限，因为多数情况下非空候选本身也答错，根因在枚举值错误而非选择器。

### 3. 已邮件请求官方测试流程

当前全部实验在 dev 集进行。已发邮件请求 BIRD 官方获取盲测数据和评测脚本，等待回复。

### 4. 逐步构建完整 Agent Harness，做对题数从 908 提升到 1213

从 GLM-5.2 直接生成（做对 908 题）出发，逐步叠加各模块，最终做对 1213 题（比基线多对 305 题）。各模块贡献：

| 模块 | 多做对 | 做法说明 |
|---|---:|---|
| 换生成器 | +160 | 从 API 大模型直推换成 4 个 BIRD 训练集微调的小模型各生成 8 条候选，用打分器选最优 |
| 候选重选 | +52 | 对做错的题，从候选池里取打分最高的 5 条，两两让模型判断哪条更对，淘汰赛选冠军 |
| 列选择修复 | +24 | 首创"列接地"：对 SELECT 子句选错列的题，查数据库列的实际样本值，让模型对比后重选 |
| 值探查修复 | +7 | WHERE 条件值错了的题，查数据库实际存的值做模糊匹配，修正大小写/补 LIKE |
| 执行修复 | +2 | 执行报错或返回空的题，把错误信息喂给模型让它重写 |
| JOIN 修复 | +4 | 用外键图的最短路径诊断该连没连、多连了哪个表 |
| 新生成器扩展 | +31 | 加入另外 3 个不同训练方式的生成器（含一个 32B 模型），每个都覆盖了一批之前全错的题 |
| 深度重新生成 | +21 | 对所有候选全错的题，用完整数据库上下文（建表语句+列样本+外键）让模型从零重新写 SQL |

## 下周计划

### 计划 1：列选择错误族修复（143 题，最大族）

1. 从训练集统计"标准答案偏好用哪个列"（比如 california_schools 数据库的答案总是用 `School` 而不是 `School Name`），构建列偏好表；
2. 对列选择错误的题，把列偏好表 + 两个候选列的实际数据样本一起喂给模型，让它选对列；
3. 预期多做对 10-20 题。

### 计划 2：JOIN 路径错误族修复（85 题，第二大族）

1. 对过度 JOIN 的 39 题，做列依赖检查：如果某张 JOIN 来的表的列在 SELECT 和 WHERE 里都没用到，说明这个 JOIN 是多余的，剪掉；
2. 对漏 JOIN 的 42 题，做实体覆盖检查：问题里提到的实体（如"管理员姓名"）不在当前 FROM 的表的列里，说明需要补 JOIN，用外键图找路径补上；
3. 预期多做对 5-15 题。

### 计划 3：引入更强生成器突破上限

1. 尝试下载 70B+ 模型（如 Qwen2.5-72B），在本地推理生成候选，看能否覆盖当前所有生成器都答错的盲区题；
2. 如果显存不够跑 70B，尝试用 4-bit 量化（45GB）通过 llama.cpp 推理；
3. 预期：如果 70B 模型的候选 oracle 覆盖超过 1381 题（90%），则 90% 目标可达。
