## 二、逐类修复路线

### 类1：不同列名（140 题）— 仍需更强列匹配

**根因**：列名歧义——同一张表有多个语义相近的列（City/MailCity、School/SName、Street/StreetAbr）。

**E3c 已修了一部分**（323→140），剩余 140 题的匹配更难：
- 跨表同义列：`schools.School` vs `frpm.School Name`（需理解两个表的关系）
- 缩写变体：`Street` vs `StreetAbr`（需知道 gold 倾向用缩写列）
- 多列对齐错误：问题问多个属性时，pred 把列对应错了

**修复路线**：
1. **列样本对比**：对歧义列对（City vs MailCity），查各自样本值，看哪个更像"城市名"
2. **gold 偏好学习**：从 train 集统计 BIRD 标注者偏好（如 california_schools 用 `School` 不用 `School Name`），构建列名偏好表
3. **LLM 带列样本重选**：给 GLM-5.2 看两列各自的样本值，让它判断哪个匹配问题意图
- 预期：+20-40（140 × 15-30%）

### 类2：JOIN 错误（111 题，63 over + 48 under）

**根因**：
- **过度JOIN（63）**：pred 多 JOIN 了一个不必要的表（如 gold 不需要 JOIN schools 表就能从 frpm 拿到答案）
- **漏JOIN（48）**：pred 没意识到需要跨表（如 gold 需要 JOIN frpm+schools 但 pred 只查 frpm）

**修复路线**：
- 过度JOIN：**列依赖检查**——检查 JOIN 的表是否有 SELECT/WHERE 列真正依赖它，若无则可剪枝
- 漏JOIN：**FK 图 + 问题实体覆盖检查**——如果问题提到的实体（如"school names"）不在当前 FROM 表的列里，需补 JOIN
- 预期：+10-25（111 × 10-22%）

### 类3：WHERE 值错误（76 题，42 wrong + 18 LIKE + 16 date）

**根因细分**：
- **完全不同的值（42）**：模型理解错了问题意图，用了错误的过滤值（如把 "district code 0613360" 写成 "0740"）
- **LIKE 模式（18）**：gold 用 `LIKE 'Riverside%'`（模糊匹配），pred 用 `= 'Riverside'`（精确匹配）
- **日期格式（16）**：gold 用 `1991-12-31`，pred 用 `2000-01-01`（完全不同的日期）或格式差异

**修复路线**：
- LIKE 模式：**值探查 + 模糊匹配建议**——如果 WHERE 值在 DB 中不精确匹配但 LIKE 能匹配，建议改 LIKE
- 日期格式：**日期列探查**——查日期列实际存储格式（`strftime` vs 原始字符串）
- 完全不同的值：**深度值接地**——对问题中的每个实体词，在 DB 全库搜 cell 值
- 预期：+15-30（76 × 20-40%）

### 类4：COUNT(*) 漏修（25 题）

**根因**：E3c 的 COUNT(*) 检测触发率不够（370 issues 中部分没覆盖到这些）。

**修复路线**：加强规则——对所有 `COUNT(*)`，检查问题是否问 "how many [具体实体]"，若是则建议 `COUNT(该实体主键列)`。需验证该列是否有 NULL。
- 预期：+5-15

### 类5：多选/少选列（21+25=46 题）

**根因**：
- 多选：pred 额外加了 School Name 等列（问题只问 phone）
- 少选：问题问 "phone and extension"，pred 只选了 phone

**修复路线**：**问题实体→列映射计数**——从问题提取请求的实体数，与 SELECT 列数对比，不匹配时增删列。
- 预期：+10-20

## 四、优先级建议

1. **不同列名（140题）**：最大单类，列样本对比 + gold偏好学习可修
2. **WHERE值错误（76题）**：LIKE模式 + 日期格式有确定性信号
3. **多选/少选列（46题）**：问题实体计数对齐，规则化

这三类共 262 题，是下一个迭代的核心目标。
